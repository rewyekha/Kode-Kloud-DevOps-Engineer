# Kubernetes Sidecar Containers

We have a web server container running the nginx image. The access and error logs generated by the web server are not critical enough to be placed on a persistent volume. However, Nautilus developers need access to the last 24 hours of logs so that they can trace issues and bugs. Therefore, we need to ship the access and error logs for the web server to a log-aggregation service. Following the separation of concerns principle, we implement the Sidecar pattern by deploying a second container that ships the error and access logs from nginx. Nginx does one thing, and it does it well—serving web pages. The second container also specializes in its task—shipping logs. Since containers are running on the same Pod, we can use a shared emptyDir volume to read and write logs.

1. Create a pod named `webserver`.
2. Create an `emptyDir` volume `shared-logs`.
3. Create two containers from `nginx` and `ubuntu` images with `latest` tag only and remember to mention tag i.e `nginx:latest`, nginx container name should be `nginx-container` and ubuntu container name should be `sidecar-container` on webserver pod.
4. Add command on sidecar-container `"sh","-c","while true; do cat /var/log/nginx/access.log /var/log/nginx/error.log; sleep 30; done"`
5. Mount the volume `shared-logs` on both containers at location `/var/log/nginx`, all containers should be up and running.

`Note:` The `kubectl` utility on the `jump-host` has been configured to work with the Kubernetes cluster.



### Kubernetes Sidecar Pattern for Log Aggregation

#### Overview

This document describes the implementation of the Sidecar pattern in Kubernetes to handle log aggregation for an Nginx-based web server. The primary container runs the Nginx service, while a secondary container (sidecar) is responsible for collecting and streaming logs.

This approach follows the principle of separation of concerns:

* The Nginx container focuses solely on serving web traffic.
* The sidecar container handles log processing and forwarding.

A shared `emptyDir` volume is used to allow both containers to access the same log files.

***

#### Objectives

* Deploy a Pod named `webserver`
* Configure an `emptyDir` volume named `shared-logs`
* Run two containers within the same Pod:
  * `nginx-container` using `nginx:latest`
  * `sidecar-container` using `ubuntu:latest`
* Mount the shared volume at `/var/log/nginx` in both containers
* Configure the sidecar container to continuously read and output Nginx logs

***

#### Architecture

* **Pod**: `webserver`
* **Volume**: `emptyDir` (ephemeral, shared across containers)
* **Containers**:
  * Nginx container writes logs to `/var/log/nginx`
  * Sidecar container reads logs from the same directory and streams them

***

#### Implementation Steps

**Step 1: Create the Pod Definition**

Create a YAML file named `webserver.yaml`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: webserver
spec:
  volumes:
    - name: shared-logs
      emptyDir: {}

  containers:
    - name: nginx-container
      image: nginx:latest
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx

    - name: sidecar-container
      image: ubuntu:latest
      command:
        - sh
        - -c
        - >
          while true;
          do
            cat /var/log/nginx/access.log /var/log/nginx/error.log;
            sleep 30;
          done
      volumeMounts:
        - name: shared-logs
          mountPath: /var/log/nginx
```

***

**Step 2: Deploy the Pod**

Apply the configuration using `kubectl`:

```bash
kubectl apply -f webserver.yaml
```

***

**Step 3: Verify Pod Status**

Check the status of the Pod:

```bash
kubectl get pods
```

Ensure the Pod shows `2/2` containers in the `Running` state.

***

**Step 4: Inspect Pod Details**

Review container configuration and volume mounts:

```bash
kubectl describe pod webserver
```

Verify:

* Both containers are running
* The `shared-logs` volume is mounted at `/var/log/nginx`

***

**Step 5: View Sidecar Logs**

Retrieve logs from the sidecar container:

```bash
kubectl logs webserver -c sidecar-container
```

This displays the contents of:

* `/var/log/nginx/access.log`
* `/var/log/nginx/error.log`

***

**Step 6: Generate Test Traffic**

To validate logging, forward a local port to the Pod:

```bash
kubectl port-forward pod/webserver 8080:80
```

In a separate terminal, send HTTP requests:

```bash
curl http://localhost:8080
curl http://localhost:8080/test
curl http://localhost:8080/demo
```

***

**Step 7: Re-check Logs**

After generating traffic, inspect logs again:

```bash
kubectl logs webserver -c sidecar-container
```

Expected output includes HTTP access entries and potential error logs.

***

#### Key Concepts

**Sidecar Pattern**

A design pattern where a secondary container enhances or extends the functionality of the primary container without modifying it directly.

**emptyDir Volume**

* Created when the Pod starts
* Shared among containers within the Pod
* Deleted when the Pod is removed
* Suitable for temporary data such as logs or cache

***

#### Conclusion

This implementation demonstrates a clean and modular approach to log handling in Kubernetes using the Sidecar pattern. By separating application logic and log processing into different containers, the system becomes easier to manage, extend, and maintain.

This pattern can be extended in production environments by integrating log shipping tools such as Fluentd, Logstash, or other observability platforms.
